# Laya Integration — Plan (Argus side)

Sibling doc: `../aegis/PROJECT_DESC.md` (Aegis-side plan). Shared
background and Phase 0 results are duplicated in both so each repo's doc
stands alone; repo-specific build steps live only in their own copy. This
is a Laya-integration planning doc, unrelated to this repo's earlier
buildathon submission — see `README.md`/`docs/DESIGN.md` for that history.

## Background

Evaluating whether [Laya](https://github.com/NandhaKishorM/laya) can sit in
front of RAGAS Faithfulness (`drift/diff.py`) as a fast, confidence-gated
first pass — decide locally when confident, escalate to the LLM judge when
not. Checkpoint decision: `laya-typed-decisions` only, CPU.

## Phase 0 results (measured on this machine)

| | median | tail |
|---|---|---|
| Laya, per question (fp32, CPU) | ~159ms | p95 266-271ms |
| RAGAS Faithfulness, per claim check (real Groq calls, n=14) | 1688ms | max 12146ms |

**Laya is ~10.6x faster at the median.** Tail is reported separately, not
folded into one range: RAGAS's own call-to-call spread was 1306-12146ms
(9.3x) on 14 back-to-back real calls with 0 failures this run — that
variance is inherent to the LLM-judge path, and it's specifically what the
cascade is expected to absorb, not just the median cost.

**Token budget, confirmed on n=18 real Gemini answers** (drift/sampler.py's
own question set, not synthetic filler): worst-case cascade state (p95
answer length + the largest real policy topic's claims, "refund" + the
question) = 127 tokens. Fits the 768-token typed-decisions budget with 6x
headroom, and even the 320-token English-checkpoint budget. No truncation
risk found.

**Calibration:** `laya-typed-decisions` ships at least one invalid
temperature (clamped by the library at load time, see Aegis-side doc for
the exact warning). Refit before trusting any confidence threshold — this
is the entire point of the confidence-gated cascade, so skipping it isn't
an option.

**bf16 CPU fails reproducibly** (dtype mismatch inside the model's own
forward pass, no public API to do it correctly) — fp32 only.

## Laya cascade — pre-flight audit (2026-09-26)

Same classes of bug that corrupted Aegis's early numbers (see sibling doc's
"Baseline findings"), checked against Argus before building the cascade on
top of it. Nothing fixed yet, per instruction — findings and proposed fixes
only.

**1. Hardcoded/unverified model names.**
- `agent/reference_agent.py:26` — `MODEL = "gemini-3.5-flash-lite"`, a bare
  string constant, no env override, three call sites (`ask`, `ask_async`,
  and the tool-calling path) all read the same global. Whether this model
  id is still current on Google's side hasn't been checked against a live
  model list. **Proposed fix:** move to `os.environ.get("GEMINI_MODEL",
  "gemini-3.5-flash-lite")`, matching the pattern already used for
  `GROQ_SIMULATOR_MODEL`, and do one live smoke call before generating the
  labeled set so a retired model fails fast and cheap rather than mid-run.
- `redteam/groq_model.py:31,46` — `DEFAULT_MODEL = "openai/gpt-oss-20b"`
  (judge), `DEFAULT_SIMULATOR_MODEL` defaults to `"qwen/qwen3.8-27b"`
  (already env-overridable via `GROQ_SIMULATOR_MODEL`). Both are the
  faithfulness-check judge path the cascade escalates to, so a stale name
  here would silently break every RAGAS-side comparison number. Names look
  internally consistent with the file's own comments and with Aegis's
  independent use of the same two models, but neither has been re-verified
  against Groq's current model list as part of this pass. **Proposed fix:**
  same live-smoke-call check before Step 2's generation run, no code change
  needed since these are already the least-hardcoded names in the repo.
- No other hardcoded model-name literals found in `agent/`, `drift/`,
  `redteam/`, or `telemetry/`.

**2. Errors/timeouts vs. pass/fail/faithful/unfaithful.** This is the
strongest area of the codebase — no instance of the Aegis bug class found.
- `drift/diff.py::check_numeric` — unparseable agent text →
  `check_status="errored"`, `flagged=None` (not `False`).
- `drift/diff.py::check_faithfulness` — any RAGAS exception is caught,
  logged with `type(exc).__name__` and message, and returns
  `check_status="errored"`, `flagged=None`. Never coerced to a score.
- `drift/self_consistency.py::check_self_consistency` — two independent
  try/excepts (sampling failure, judge failure), both → `errored`,
  `flagged=None`.
- `redteam/scoring.py::outcome()` — `tc.error` → `"errored"`, and
  `CategoryASR.asr_pct` explicitly excludes `errored` from its denominator
  (`scored = bypassed + defended`), covered by `scoring.py`'s own `demo()`
  assertions.
- `redteam/groq_model.py` — `RateLimitError` retried using the real
  `retry-after` value; `BadRequestError` retried only for the confirmed-
  transient empty-generation case (`_is_empty_generation`), everything else
  (including a real model refusal) re-raises rather than being silently
  scored. This is exactly the Aegis "refusal counted as a fixed outcome"
  bug, and it's handled correctly here.
- `agent/reference_agent.py` — Gemini 429s retried with a fixed backoff on
  top of proactive pacing; all other errors propagate uncaught.
- No fixes needed in this category.

**3. Reasoning-model judges with too-small `max_tokens`.** Found one real
issue.
- `drift/diff.py::check_faithfulness` builds its RAGAS scorer via
  `llm_factory(DEFAULT_MODEL, client=_judge_client())` with **no
  `max_tokens` override**. `DEFAULT_MODEL` is `openai/gpt-oss-20b`, a
  reasoning model. Reading `ragas/llms/base.py` directly: `llm_factory`
  defaults to `max_tokens=1024`, and its own docstring warns this "may not
  be sufficient" for reasoning models, recommending 4096+. Critically,
  this call path does **not** go through `GroqModel`'s `_kwargs()`, so it
  never sets `reasoning_format: "hidden"` the way `redteam/groq_model.py`
  does for every other Groq call in this repo — gpt-oss-20b's reasoning
  tokens are neither hidden nor exempted from the 1024-token budget here,
  so on some fraction of calls the reasoning alone could exhaust the
  budget before RAGAS's claim-decomposition JSON is emitted, producing a
  truncated or empty completion. `check_faithfulness`'s own comment
  (`drift/diff.py:111-115`) notes "2/14 faithfulness checks errored with
  nothing to diagnose from" from a real sampler run — plausibly this bug,
  though not confirmed; the fix should ship before Step 4's RAGAS-only
  baseline is trusted, since a silently-truncated judge would inflate
  RAGAS's own `errored` count for reasons unrelated to the cascade.
  **Proposed fix:** pass `max_tokens=4096` (matching `GroqModel`'s own
  `MAX_COMPLETION_TOKENS`) into `llm_factory(...)`, and check whether
  ragas's OpenAI-compatible wrapper exposes an `extra_body`/
  `reasoning_format` passthrough to hide reasoning tokens the same way
  `GroqModel._kwargs()` does. Not applying this now per instruction, but
  it should land before Step 4, not deferred to Step 5.
- `drift/self_consistency.py`'s judge goes through `GroqModel.a_generate`,
  which does set `max_tokens=4096` + `reasoning_format="hidden"`. No issue.

**4. Caching / shared state across runs.**
- No `lru_cache`, `functools.cache`, or module-level result cache found
  anywhere in `agent/`, `drift/`, `redteam/`, or `telemetry/`.
- `agent/reference_agent.py::load_ground_truth()` re-reads
  `catalog.json`/`policies.json` from disk on every call by design —
  `drift/staged_injection.py` depends on exactly this to prove the agent
  can never itself go stale mid-session.
- Shared state that *is* present, deliberately, and is not the same class
  of bug: `agent/reference_agent.py`'s `_last_call_at`/`_RATE_LIMIT_LOCK`
  (Gemini pacing) and `redteam/groq_model.py`'s `_REQUEST_LOCK` (Groq
  pacing) serialize outbound calls to stay under free-tier RPM/TPM caps.
  These make concurrent runs slower, not non-independent — each call still
  hits the live model fresh. Unlike Aegis's `SemanticCache`, nothing here
  reuses a prior verdict for a new input. No fix needed, and nothing
  analogous needs to be avoided when building the cascade scripts, as long
  as `laya_calibrate.py`/`laya_threshold_sweep.py` don't memoize a Laya
  verdict keyed on input text across calibration/sweep/test rows (nothing
  like that exists yet — noted only as a rule to follow when writing them).

**Net:** category 2 (error handling) is already correct throughout; category
4 (caching) has nothing to fix. Categories 1 and 3 have concrete, scoped
fixes — the `max_tokens`/reasoning-format fix in particular should land
before Step 4's RAGAS-only baseline number is reported, since it can
change that baseline's own error rate independent of anything Laya does.

## Laya cascade — plan for steps 2-5 (2026-09-26, plan only, not built)

**Deviation flagged up front:** the original ask names
`drift/staged_injection.py` as the tool to generate faithful/unfaithful
claim variants. Reading it: it's the Step 19 git-history staleness demo
(prod_003's price edited, committed, and re-verified against
`drift_cause` classification) — it has no paraphrase or claim-corruption
generation capability at all, and reusing it as written would not produce
the ~210-row variant set. **Proposed instead:** a new module,
`drift/faithfulness_variants.py`, that calls the existing Groq judge/
simulator models (`redteam/groq_model.py`) to generate, per claim, a
faithful paraphrase and four unfaithful transforms (stale number,
fabricated exception, contradicted claim, unsupported addition) via a
structured-output schema (mirroring `GroqModel.generate(..., schema=...)`,
already used by `ConsistencyVerdict` in `drift/self_consistency.py`). This
keeps every generation call within the repo's existing Groq client/retry/
schema machinery rather than adding a new path.

### Step 2 — labeled faithfulness set

**Files:**
- Create `drift/faithfulness_variants.py` — `generate_variants(claim: dict)
  -> list[VariantRow]`, one call per claim per variant type (5 calls x 14
  claims = 70 Groq calls to produce ~15 rows/claim via light rephrasing of
  each transform, or fewer calls each returning multiple phrasings per
  schema — exact call count to be finalized against the Groq TPD budget,
  see Risks). Each `VariantRow` carries `row_id`, `claim_id`, `topic`,
  `variant_type` (`faithful_paraphrase` | `stale_number` |
  `fabricated_exception` | `contradicted_claim` | `unsupported_addition`),
  `intended_label` (`faithful` | `unfaithful`), `question`
  (`_faithfulness_question(topic)`, reused from `drift/sampler.py`),
  `context_claims` (all claims under that topic, matching
  `check_faithfulness`'s existing multi-claim-context requirement), and
  `answer` (the generated variant text, standing in for what the agent
  "said").
- Create `data/faithfulness_variants.jsonl` — the generated rows.
- Create `scripts/generate_faithfulness_review.py` — reads
  `data/faithfulness_variants.jsonl` plus ~20 fresh live-agent rows
  (`ask_async` over each of the 5 topic questions, 4x each, labeled
  `unknown`, reusing `drift/sampler.py::_faithfulness_question` — not the
  numeric or self-consistency questions, since scope is faithfulness
  only), and writes `data/faithfulness_review.md`: one row per line —
  `row_id | claim_id | topic | variant_type | intended_label | question |
  claims | answer` — for manual review.
- Create `data/faithfulness_splits.json` — `{claim_id: "calibration" |
  "sweep" | "test"}` for all 14 claims, chosen to keep each of the 5
  topics represented across splits where the topic's claim count allows
  it (refund/shipping have 4 claims each, warranty/cancellation/discount
  have 2 each) — target ~4/6/4 claim counts on calibration/sweep/test.
  Exact assignment proposed in the review doc for confirmation alongside
  the row labels, not decided silently.

**Order:** write `faithfulness_variants.py` → generate the ~210 rows →
sample ~20 live-agent rows → write the review doc + proposed split →
**stop, wait for row-id flips/drops.**

**Must-have:** the review doc and proposed split. **Stretch:** none — this
step is entirely prerequisite to everything after it.

**Risks:**
- Groq free-tier daily token cap (TPD) is a known rolling-24h constraint
  on this project (see `BUGS.md`); ~210 variant-generation calls plus ~20
  live-agent-judge calls is small relative to the red-team harness's own
  usage, but should be sequenced to avoid colliding with a same-day
  red-team run.
- Variant quality depends on the generator model actually producing a
  usable stale-number/fabricated-exception/etc. rather than refusing or
  drifting off-schema — `redteam/groq_model.py`'s existing retry/schema
  handling covers the mechanical failure case, but a generated row that's
  technically valid JSON yet doesn't match its intended label is a
  labeling-quality risk the review doc is specifically for.

**Step 2 results (2026-09-26, built in `drift/faithfulness_variants.py`):**
- Single file, not a separate `scripts/generate_faithfulness_review.py` -
  folded the review-doc writer into the same module (fewer files, same
  behavior).
- **Rebalanced after the first pass:** the initial run (1 faithful type x
  3 styles vs. 4 unfaithful types x 3 styles) produced 41 faithful vs. 166
  unfaithful rows - an accuracy-rewards-always-guessing-unfaithful set.
  Fixed by adding `FAITHFUL_PARAPHRASE_INSTRUCTIONS`, 4 differently-worded
  full-fidelity paraphrase instructions (same count as the 4 unfaithful
  types), so faithful and unfaithful land at 12 rows/claim each before
  dedup. Final counts: 162 faithful (`faithful_paraphrase`) vs. 164
  unfaithful (40 `stale_number` + 42 `fabricated_exception` + 40
  `contradicted_claim` + 42 `unsupported_addition`), 326 rows total after
  dedup (of 336 generated, 10 near-duplicates removed) + 20 live-agent
  rows labeled `unknown`.
- **Automated consistency checks** (advisory only, nothing auto-dropped):
  `stale_number` and the numeric half of `faithful_paraphrase` are
  deterministic (regex number extraction - does the answer's number set
  differ from / stay a subset of the claim's); `contradicted_claim`,
  `fabricated_exception`, `unsupported_addition`, and the non-numeric half
  of `faithful_paraphrase` go through a separate short LLM prompt
  (`check_substance`, its own schema and prompts, not RAGAS and not the
  variant generator's own prompt) asking only "did the intended
  transformation actually happen". **Disclosed deviation:** the first
  version of the `faithful_paraphrase` check used literal word-overlap
  (no number or content word outside the claims) and flagged 136/162
  (84%) of rows - almost all harmless synonyms ("send back" for "return",
  "arrival" for "delivery"). Literal token matching can't distinguish a
  synonym from a real unsupported addition, so that half moved to the LLM
  check too (numbers stayed deterministic, since literal number matching
  is reliable). Final run: 50/326 rows flagged (15%) - 39
  `faithful_paraphrase`, 5 `stale_number`, 5 `contradicted_claim`, 1
  `unsupported_addition`, 0 `fabricated_exception`.
- A judge-model hiccup surfaced during this: `openai/gpt-oss-20b`
  occasionally emits its full chain-of-thought as plain text past
  `reasoning_format="hidden"`, which Groq's strict-schema mode then
  rejects with `output_parse_failed` (a different error code than the
  `json_validate_failed` case `redteam/groq_model.py`'s own retry logic
  already handles). Uncaught, this crashed the whole automated-check
  batch on one bad row. Fixed in `run_automated_checks`: a `check_substance`
  exception is caught, logged, and the row is flagged with the error as
  its reason rather than crashing the run - same "never let a check
  failure discard the rest of the batch" posture as `drift/sampler.py`'s
  own per-row logging try/except.
- `data/faithfulness_review.md` structure: a "Flagged by automated
  checks" section first (row + reason), then the remaining rows grouped
  by `variant_type`, then the 20 live-agent rows last - a flagged row
  appears once, in the flagged section only.

**Labeling rule (user-confirmed, 2026-09-27), applied by manual review of
`data/faithfulness_review.md`:**
- **Faithful:** everything the answer states is supported by the claims.
  Omitting other claims is fine. Generic courtesy lines ("let us know if
  you have questions") are fine.
- **Unfaithful:** adds a fact, condition, number, promise, or process not
  in the claims, or makes a blanket statement that contradicts another
  claim (e.g. "every order pays 99 rupees" vs. free shipping above 999).
- **Dropped:** borderline cases - speculation about future changes, vague
  hedges, outcomes borrowed from another topic.

**Checker bugs found by this review (not re-run - the manual review
already corrected their output, see below):**
- The LLM substance check treated *omission* as unfaithfulness - most of
  the 39 flagged `faithful_paraphrase` rows were paraphrases that
  correctly stuck to one claim's content but didn't restate every other
  claim under the same topic, which the check's prompt didn't distinguish
  from a genuine unsupported addition.
- The `stale_number` regex (`_NUMBER_RE`, digits only) missed number
  *words* - a corruption changing "one" to "two" has no digit for the
  regex to compare, so it can't detect that class of stale-number variant.
- The single `unsupported_addition` flag was a correct row (false
  positive on the checker's part, not a real issue with the data).

**Review outcome, applied via `scripts/apply_faithfulness_review.py`**
(kept as a script rather than an ad-hoc edit, so each row's relabeling
traces to a specific line in the review reply rather than a silent
hand-edit): 17 rows flipped `faithful` → `unfaithful`, 20 rows dropped
(all borderline per the rule above), all 20 live-agent rows labeled
`faithful` (near-verbatim policy recitations) and reported as a separate
group in every result table, never pooled into the main faithful/
unfaithful metrics. Every other flagged row keeps its original intended
label - the checker was wrong on all of them per the bugs above.

Final counts (variants only, 306 rows after the 20 drops, excludes the 20 live rows):
**128 faithful / 178 unfaithful.** By split: calibration 30f/58u (88),
sweep 62f/72u (134), test 36f/48u (84). The class balance shifted toward
unfaithful again after review (was ~50/50 pre-review) - real corrections
outweighed the rebalancing effort, which is expected: the automated
generator's rebalancing targeted raw counts, not review-verified counts.
`laya_calibrate.py` (Step 3) still class-balances its own calibration-split

### Step 3 — cascade design (plan only)

**Files (not yet built):**
- `redteam/laya_cascade.py` — `load_laya_agent()` (module-level singleton,
  same pattern as Aegis's `laya_second_stage.py`), `laya_faithfulness_verdict
  (question, context_claims, answer) -> LayaVerdict(p_faithful: float,
  raw: dict)` using a `noul` question ("is every claim in the answer
  supported by the given policy claims?"), and
  `cascade_check_faithfulness(question, policy_id, claim, response,
  context_claims, threshold) -> DriftCheckResult` — the actual gate:
  decides alone when `max(p, 1-p) >= threshold`; otherwise calls the
  existing `drift/diff.py::check_faithfulness` unchanged. If the
  escalation call raises, the returned `DriftCheckResult` is
  `check_status="errored"`, and the Laya-only verdict that would have been
  given is logged alongside it (not silently dropped) — this is the
  "Laya-only fallback" path the spec asks for.
- `redteam/laya_calibrate.py` — fits temperature on the **calibration**
  split only (from `data/faithfulness_splits.json`), class-balanced
  (faithful vs. unfaithful), reports ECE per class to stdout and to
  `data/laya_faithfulness_calibration.json`. Per the standing rule: if
  benign/faithful-side ECE gets worse after fitting, the report says so
  plainly rather than describing the result as "calibrated."
- `redteam/laya_threshold_sweep.py` — loads the **sweep** split only.
  Threshold rule, fixed before Step 4: the **lowest** `t` such that cascade
  **balanced accuracy** (mean of faithful recall and unfaithful recall)
  against the verified labels is no more than 5 points below RAGAS-only
  balanced accuracy on the same sweep rows. Changed from plain accuracy
  (2026-09-26): the faithfulness set is a real classification problem
  with two classes, and plain accuracy on an unbalanced or near-balanced
  set can reward a rule that leans toward one label — balanced accuracy
  weights both classes' recall equally regardless of how many rows of
  each end up in a given split. If no `t` in the grid satisfies this, the
  script reports that explicitly and picks nothing — no relaxation.
  Writes the full curve (`t`, cascade balanced accuracy, RAGAS-only
  balanced accuracy, % handled by Laya alone) to
  `data/laya_faithfulness_threshold_sweep.jsonl`, chosen `t` marked.

**Order:** `laya_cascade.py`'s decide/escalate logic first (it's a pure
function apart from the two model calls it wraps) → `laya_calibrate.py`
against the calibration split → `laya_threshold_sweep.py` against the
sweep split, consuming the fitted temperature.

**Must-have:** the cascade function, the fixed threshold rule exactly as
specified (including the no-relaxation behavior), the Laya-only fallback
log on escalation error. **Stretch:** none identified — all four pieces
are load-bearing for Step 4.

**Risks:**
- 14 claims total means the sweep split (~6 claims) may produce a thin
  row count once split by claim — the threshold curve and its "5 points
  below RAGAS-only" comparison will have correspondingly wide uncertainty;
  worth reporting alongside the curve, not just the chosen `t`.
- The Step 1 `max_tokens` fix (category 3 above) should land before this
  step runs, since `laya_threshold_sweep.py`'s "RAGAS-only balanced
  accuracy on these rows" reference number is exactly the number that bug
  can distort. **Done** (2026-09-26, see commit `e1d73e8`).

**Step 3 results (2026-09-27), method: score once, save, simulate from
saved scores** - `redteam/laya_score_faithfulness.py` scored all 326 rows
(calibration + sweep + test + live) with Laya once; `redteam/ragas_score_faithfulness.py`
scored the 238 sweep/test/live rows with RAGAS once (calibration is
Laya-only, no RAGAS baseline needed there). Every number below comes from
replaying those saved per-row scores/latencies, not from re-running
either model - the cascade "decides" by reading a saved Laya confidence
and, on escalation, a saved RAGAS result, with latency summed from both
saved numbers on escalated rows.

- **Laya latency** (326 rows, single-question forward pass, CPU fp32):
  p50=661ms, p95=1414ms. Notably higher than Phase 0's ~159ms/271ms
  estimate - Phase 0's number amortized a 5-question `guard_questions()`
  batch call; a single-question call here still pays the same fixed
  per-forward-pass overhead, so it doesn't scale down with fewer
  questions. Real measured number now supersedes the Phase 0 estimate.
- **RAGAS latency** (238 rows): p50=1655ms, p95=11420ms, 0 errored -
  consistent with Phase 0's own RAGAS measurement.
- **Calibration** (88 calibration-split rows, 30 faithful/58 unfaithful,
  class-balanced NLL fit): **T=0.72**, but ECE got WORSE after fitting
  for BOTH classes (combined 0.2057→0.2344, faithful 0.1404→0.1745,
  unfaithful 0.2394→0.2654). Per the standing rule, Laya's confidence is
  NOT described as calibrated anywhere in this cascade - the fitted T is
  still used for the threshold-sweep's decision rule (ranking, not
  calibration, is what the rule relies on), but no downstream number
  claims calibrated probabilities.
- **Sweep-split baselines (134 rows)**, balanced accuracy with its
  approximate CI (mean of the two per-class recall Wilson CIs) and
  per-class precision/recall:

  | Baseline | Balanced accuracy | faithful P/R | unfaithful P/R |
  |---|---|---|---|
  | A: RAGAS-only @ 0.7 (existing) | 0.8098 [0.711, 0.876] | 0.932 / 0.661 | 0.767 / 0.958 |
  | B: RAGAS-only, tuned on sweep (t=1.0) | 0.8168 [0.721, 0.879] | 0.953 / 0.661 | 0.769 / 0.972 |
  | C: Laya-only @ P(faithful)≥0.5 | 0.7744 [0.674, 0.843] | 0.670 / 0.952 | 0.935 / 0.597 |

  RAGAS's own tuned threshold (t=1.0) is a degenerate result worth
  flagging: RAGAS's sweep-split scores separate the two classes cleanly
  enough that requiring a perfect 1.0 score for "faithful" still beats
  every lower threshold on balanced accuracy - not necessarily true on
  test. 0 RAGAS errors on sweep.
- **Threshold sweep** (51 thresholds, t=0.50-1.00, rule: lowest t with
  cascade balanced accuracy ≥ tuned-RAGAS − 0.05 = 0.7668): **chosen
  t=0.50.** This is a real but somewhat degenerate result: `max(p, 1-p)
  ≥ 0.5` is true for every row by construction, so t=0.50 makes the
  cascade decide alone on 100% of rows (134/134 calls saved) - it
  collapses to exactly Baseline C (balanced accuracy 0.7744), which
  already clears the bar without ever escalating. The full curve shows
  the cascade CAN beat both RAGAS baselines at higher t (peak 0.8732 at
  t=0.80, handling 41.8% alone), but the rule optimizes for the lowest
  qualifying t, not the peak - it picks the cheapest option that clears
  the bar, not the best one. 0 escalation errors throughout the curve
  (RAGAS never errored on sweep). Full curve: `data/laya_faithfulness_threshold_sweep.jsonl`.
- **Resolved (2026-09-27) — two operating points, both fixed before
  touching test:**
  - **Cost point, t=0.50** - from the original lowest-t rule. Laya
    decides every row alone; this is the cheapest point that still clears
    the balanced-accuracy bar.
  - **Accuracy point, t=0.80** - the threshold that maximized cascade
    balanced accuracy on the sweep curve (0.8732, 41.8% handled alone).
  - **Disclosed explicitly:** the accuracy point was added AFTER seeing
    the sweep curve - it is not blind to sweep in the way the cost point
    is. It was picked by eyeballing the curve's peak, not by an
    independent pre-registered rule. The test split was untouched when
    both points were fixed - this order (see two rows above) is what
    keeps the test-split numbers honest despite the accuracy point being
    curve-selected.
  - **Named limitation:** t=0.80 was selected as the best of 51
    thresholds evaluated on 134 sweep rows. Some optimism on test is
    expected purely from that selection - a curve-picked maximum
    regresses toward the mean on a fresh sample, and 134 rows leaves
    real sampling noise in exactly where the true peak sits. Report the
    accuracy point's test-split number as "test result for the
    sweep-selected point," not as an independent confirmation that 0.80
    is the true optimal threshold.

- **RAGAS false alarms on sweep, investigated (2026-09-27):** RAGAS
  wrongly flags 21/62 (33.9%) of sweep-split faithful rows as unfaithful
  at its 0.7 threshold - all 21 are `faithful_paraphrase` rows, 0 from any
  other type. This repo's ragas version doesn't expose per-statement
  verdicts (`result.reason` and `result.traces` are both `None` on
  `Faithfulness.ascore()` output - checked directly), so the pattern below
  is inferred from the score fractions (0.5 ≈ 1 of 2 decomposed
  sub-claims judged unsupported, 0.333 ≈ 1 of 3, 0.0 ≈ all) plus manual
  reading, not a retrieved list of which exact statements RAGAS rejected.

  Six examples (answer / claims / score):
  1. **score=0.5** - *"Sure thing! We'll need a valid order ID before we
     can issue any refunds."* vs. claims incl. "A valid order ID is
     required to process any refund." - the claim is stated almost
     verbatim; RAGAS still splits the sentence into two propositions
     ("an order ID is needed" + an implicit "we will issue refunds"
     promise) and can't verify the second against a literal bullet.
  2. **score=0.667** - *"...you are welcome to exchange such items for
     other products. Please contact customer support to arrange an
     exchange."* vs. "...not eligible for refund, only exchange." - the
     added operational detail ("contact customer support to arrange it")
     is a reasonable inference from "only exchange," not a new fact, but
     reads as its own unverifiable sub-claim.
  3. **score=0.0** - *"Hey! Just a heads-up - if you bought something in
     our clearance sale, we can't offer a refund, but you're welcome to
     exchange it for another item."* - same claim as #2, fully accurate,
     scored 0.0. The friendly framing ("Hey! Just a heads-up") is the
     likeliest extra "claim" being counted and failing verification -
     this is the clearest case matching conversational filler getting
     treated as a claim.
  4. **score=0.333** - *"For any purchase that totals more than 999
     rupees, customers are eligible for free standard shipping. This
     means we'll handle the shipping cost at no additional charge, so you
     only pay for your items."* vs. "Orders above 999 rupees qualify for
     free standard shipping." - the elaboration ("we'll handle the cost,"
     "you only pay for items") restates the same fact in different words
     but reads as 1-2 additional unverifiable propositions.
  5. **score=0.333** - *"Under our standard domestic shipping policy,
     orders are delivered within 3-5 business days. This timeframe
     accounts for typical processing times and logistics, ensuring
     timely receipt of your purchase."* vs. "Standard domestic delivery
     takes 3 to 5 business days." - same pattern: an explanatory second
     sentence that adds no new fact still counts against the score.
  6. **score=0.5** - *"If you change your mind before it ships, just let
     us know and we'll cancel it - no fee at all!"* vs. "Orders can be
     cancelled free of charge only before they have shipped." - "just let
     us know" (a generic courtesy/process line) is plausibly the second
     decomposed claim RAGAS can't verify.

  **Pattern: conversational/detailed-style elaboration, not fabrication.**
  Every one of the 21 flagged rows is a `faithful_paraphrase` row in the
  `conversational` or `detailed` style (never `short`) - the styles that
  add courtesy framing or an explanatory second sentence. RAGAS's claim
  decomposition splits these into multiple atomic propositions and
  penalizes any clause that paraphrases-with-elaboration rather than
  restating a claim near-verbatim, even when nothing false or unsupported
  was actually said. This matches the labeling rule's own "generic
  courtesy lines are fine" carve-out almost exactly - RAGAS doesn't make
  that carve-out, humans reviewing this set did.

**Step 4 follow-up (2026-09-27), all from saved test scores, no new
calls** (`redteam/laya_test_analysis.py`):

*McNemar exact test (discordant pairs, two-sided binomial, p=0.5):*

| Comparison | A-right/B-wrong | A-wrong/B-right | p-value |
|---|---|---|---|
| cascade@0.80 vs RAGAS@0.7 | 5 | 0 | 0.0625 |
| cascade@0.80 vs Laya-only | 10 | 5 | 0.3018 |
| Laya-only vs RAGAS@0.7 | 10 | 10 | 1.0000 |

None of the three pairwise differences reach p<0.05 on this n=84 test
split - the cascade-vs-RAGAS gap (5 vs 0 discordant, the closest to
significant) would need a larger sample to confirm as more than noise.
**Read the balanced-accuracy table above as suggestive, not statistically
confirmed, given this sample size.**

*Per-claim balanced accuracy (4 test claims):*

| Claim | n | RAGAS@0.7 | Laya-only | cascade@0.80 |
|---|---|---|---|---|
| `policy_cancellation_shipped` | 20 | 0.8125 | 0.7917 | **0.8750** |
| `policy_refund_processing_time` | 23 | 0.9091 | 0.9091 | **1.0000** |
| `policy_shipping_international` | 19 | 0.7949 | **0.9231** | 0.8782 |
| `policy_warranty_exclusions` | 22 | 0.9091 | **0.9545** | **0.9545** |

**The cascade's advantage does NOT hold on every claim.** It wins or ties
on 3 of 4 (`cancellation_shipped`, `refund_processing_time` - perfect
score, `warranty_exclusions` - tied with Laya-only), but on
`policy_shipping_international` pure Laya-only (0.9231) beats the cascade
(0.8782), which in turn still beats RAGAS-only (0.7949). The overall
test-set win is not uniform across claims - one claim's escalations to
RAGAS actively hurt the cascade relative to just trusting Laya alone
there.

*Latency, explained:* Laya per-row on test: **mean=769ms**, p50=537ms,
p95=1408ms - notably higher than Phase 0's ~160ms/271ms estimate. The gap
is the batching, not the input: Phase 0's number came from
`guard_questions()`, a 5-question batch in one forward pass, divided by 5
to get a "per question" figure - that amortizes one fixed per-call cost
(tokenization + a CPU forward pass) across 5 answers. Every call in this
step asks exactly ONE question (`faithfulness`), so it pays that same
fixed overhead alone, undivided - it was never going to land near the
Phase 0 number, because Phase 0 measured a different call shape. State
serialization (question + all of a topic's claims + the answer, as JSON)
is somewhat longer than a bare `text` field too, but the 5x batching
divisor is the dominant factor, not input length. **Cost point
(t=0.50) = pure Laya, same numbers: mean=769ms, p50=537ms, p95=1408ms.
Accuracy point (t=0.80): mean=3237ms, p50=1845ms, p95=11802ms** (escalated
rows add RAGAS's own latency on top).

**Value split, stated plainly:** the accuracy point (t=0.80) buys
+0.069 balanced accuracy over RAGAS-only (0.9340 vs 0.8646, not
statistically confirmed per McNemar above) plus 38.1% fewer LLM calls
(32/84 handled by Laya alone) - but it is SLOWER per check than RAGAS
alone would suggest at first glance is impossible: 62% of rows still pay
Laya's latency ON TOP OF RAGAS's, so mean latency (3237ms) is higher than
RAGAS-only's own mean would be. **The latency win belongs to the cost
point** (t=0.50, mean=769ms, ~4.2x faster than the accuracy point), not
the accuracy point - a deployment choosing the accuracy point is trading
latency for accuracy and call-count savings, not getting all three.

**Two additional findings for the record:**
- **RAGAS threshold overfitting, confirmed:** the sweep-tuned threshold
  (t=1.0) scored WORSE on test (0.8368 balanced accuracy) than the
  existing default (t=0.7, 0.8646) - the threshold that looked best on
  134 sweep rows didn't generalize, a direct demonstration of why the
  threshold rule is fit on sweep and evaluated on test rather than picked
  and reported from the same split.
- **RAGAS false-alarm pattern** (documented in Step 3 above): 33.9% of
  sweep faithful rows wrongly flagged, concentrated entirely in
  `faithful_paraphrase` conversational/detailed variants, from claim
  decomposition penalizing courtesy framing and explanatory elaboration
  as unverifiable sub-claims. Carried forward here as a standing finding,
  not just a sweep-split curiosity - it plausibly explains part of why
  RAGAS-only's faithful recall (0.75 @ 0.7, 0.694 tuned) trails its own
  unfaithful recall (0.979 both) on test too.
