## Background

Evaluating whether [Laya](https://github.com/NandhaKishorM/laya) can sit in
front of RAGAS Faithfulness (`drift/diff.py`) as a fast, confidence-gated
first pass — decide locally when confident, escalate to the LLM judge when
not. Checkpoint decision: `laya-typed-decisions` only, CPU.

## Phase 0 results (measured on this machine)

| | median | tail |
|---|---|---|
| Laya, per question (fp32, CPU) | ~159ms | p95 266-271ms |
| RAGAS Faithfulness, per claim check (real Groq calls, n=14) | 1688ms | max 12146ms |

**Laya is ~10.6x faster at the median.** Tail is reported separately, not
folded into one range: RAGAS's own call-to-call spread was 1306-12146ms
(9.3x) on 14 back-to-back real calls with 0 failures this run — that
variance is inherent to the LLM-judge path, and it's specifically what the
cascade is expected to absorb, not just the median cost.

**Token budget, confirmed on n=18 real Gemini answers** (drift/sampler.py's
own question set, not synthetic filler): worst-case cascade state (p95
answer length + the largest real policy topic's claims, "refund" + the
question) = 127 tokens. Fits the 768-token typed-decisions budget with 6x
headroom, and even the 320-token English-checkpoint budget. No truncation
risk found.

**Calibration:** `laya-typed-decisions` ships at least one invalid
temperature (clamped by the library at load time, see Aegis-side doc for
the exact warning). Refit before trusting any confidence threshold — this
is the entire point of the confidence-gated cascade, so skipping it isn't
an option.

**bf16 CPU fails reproducibly** (dtype mismatch inside the model's own
forward pass, no public API to do it correctly) — fp32 only.

## Known limitations carried into Phase 1

- fp32 CPU only.
- Shipped calibration is invalid for at least one question type.
- **Resolved, 2026-09-25 — this repo's Supabase project is back online.**
  It stopped resolving at some point before 2026-09-24 (NXDOMAIN), user
  restarted it 2026-09-25, and it now resolves to real IPs and accepts a
  real read: `client.table("runs").select("*").limit(3)` returned 3 real
  rows (`run_type="redteam"`, dated 2026-08-24 through 2026-08-26).
  **No longer a blocker** — any Argus step that reads/writes Supabase
  history can proceed.
- The ~100-row hand-labeled faithfulness set (once built) measures
  detection of drift patterns generated by this repo's own
  `drift/staged_injection.py` — a synthetic, self-authored drift corpus,
  not verified real-world drift. Treat any accuracy number from it as a
  ceiling on this specific injected-pattern family, not a general claim.

## Phase 1 — Argus build order

1. *(Aegis-side, see sibling doc)*
2. **Calibration script** (shared implementation, run separately per
   project) — temperature refit on Argus's own calibration split only.
3. *(Aegis-side)*
4. **Hand-label scaffold** — ~100 rows generated from the 14 real policy
   claims via `drift/staged_injection.py` (some faithful paraphrases, some
   deliberately drifted), user hand-verifies true/false. Split **by claim,
   not row** — roughly 4/6/4 of the 14 claims across
   calibration/sweep/test, so paraphrase variants of the same claim never
   cross a split boundary. `threshold_sweep.py`: per threshold, reports %
   of faithfulness checks Laya handles alone, accuracy vs judge-only
   baseline, LLM calls saved, latency saved, **and** how many checks still
   produce a decision when the escalation call to RAGAS fails outright
   (Laya-only fallback count) — the Gemini 503 outage hit during Phase 0's
   own data collection, this is a real failure mode, not hypothetical.
   `laya_cascade.py`: the actual gate — Laya decides when confidence
   crosses the fitted threshold, else escalates.
   **Blocked on Supabase status** for anything that needs to read/write
   `drift_incidents` history; the hand-label set itself and the sweep can
   run entirely locally without it.
5. **Dashboard** — last. Reliability diagram (pre/post temperature fit) +
   the threshold tradeoff curve.
